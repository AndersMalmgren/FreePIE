# CLAUDE.md

Guidelines for Claude Code when working in the FreePIE repository.

## Project overview

FreePIE (Programmable Input Emulator) bridges and emulates input devices. Users write IronPython scripts in a WPF editor; the scripts read from and write to device plugins (mouse, keyboard, joystick, vJoy, Wiimote, TrackIR, Android, ...).

- .NET Framework 4.8, C# (no `LangVersion` set, so C# 7.3 is the ceiling)
- Old-style (non-SDK) `.csproj` files with `packages.config`
- IronPython 2.7.5 as the script engine, Ninject for DI, Caliburn.Micro (MVVM) + AvalonDock + AvalonEdit for the GUI
- MSTest + Rhino Mocks for tests
- License: GPLv2

### Solution layout

| Project | Purpose |
|---|---|
| `FreePIE.Core.Contracts` | Public plugin API (`IPlugin`, `GlobalType`/`Global` attributes, `Deprecated`). Third-party plugins compile against this, so treat changes as breaking. |
| `FreePIE.Core` | Script engine (`ScriptEngine/Python`), code completion and AST analysis, globals/script helpers, persistence, settings, `EventAggregator`, Ninject bindings in `Services/ServiceBootstrapper.cs` |
| `FreePIE.Core.Plugins` | Built-in device plugins (`*Plugin.cs` + a `*Global` class exposed to scripts). Help files in `Help/*.rtf` |
| `FreePIE.GUI` | WPF app: `Shells/`, `Views/` (View + ViewModel pairs), `Events/`, `Result/` (Caliburn coroutines), `Bootstrap/` |
| `FreePIE.GUI.CodeCompletion` | Completion popup control for AvalonEdit |
| `FreePIE.Console` | Headless console host |
| `FreePIE.Tests.Core`, `FreePIE.Tests.Core.Plugins` | Unit tests |
| `FreePIE.Tests.Test` | Test infrastructure (`TestBase` with Ninject kernel + Rhino Mocks helpers) |
| `Lib/` | Third-party binaries (IronPython, SlimDX, vJoy, SDKs). Do not modify. |
| `BuildTools/` | Installer/version build scripts (WiX, MSBuild). |

## Build and test

Use the `Mixed Platforms` solution platform. Building with `Platform=x86` skips projects and fails with misleading "namespace 'Core' does not exist" errors.

```bash
"/c/Program Files/Microsoft Visual Studio/2022/Community/MSBuild/Current/Bin/MSBuild.exe" FreePIE.sln "-p:Configuration=Debug" "-p:Platform=Mixed Platforms" -m -v:minimal -nologo
```

```bash
"/c/Program Files/Microsoft Visual Studio/2022/Community/Common7/IDE/Extensions/TestPlatform/vstest.console.exe" FreePIE.Tests.Core/bin/Debug/FreePIE.Tests.Core.dll FreePIE.Tests.Core.Plugins/bin/Debug/FreePIE.Tests.Core.Plugins.dll /Platform:x86
```

Add `/Tests:<Name>` to run a single test. The assemblies are x86 (SlimDX, native SDKs), so tests must run as x86.

All tests are expected to pass. Tests must not depend on hardware or drivers being installed.

`VersionInfo.cs` is generated by the build tools and git-ignored.

## Working with the project files

- **New source files must be added to the `.csproj` manually** as `<Compile Include="..." />` (XAML as `<Page>` + `<Compile ... DependentUpon>`), placed next to the other files from the same folder. MSBuild won't pick up files that aren't listed.
- New services must be bound in `ServiceBootstrapper` (Core) or the GUI `BootStrapper`.
- New plugins go in `FreePIE.Core.Plugins`, inherit `Plugin`, are decorated with `[GlobalType(Type = typeof(XxxGlobal))]`, and get a help file in `Help/`.
- Keep `FreePIE.Core.Contracts` backward compatible. Mark obsolete script-facing members with `[Deprecated(...)]` instead of removing them.
- Don't add NuGet packages or upgrade framework/library versions without asking.

## Coding style

Follow the style of the surrounding code. When in doubt, copy what the nearest similar file does. Do not reformat or "modernize" code you are not otherwise changing.

### Formatting
- 4 spaces, no tabs. CRLF line endings, UTF-8 with BOM (match existing files).
- Allman braces (opening brace on its own line) for types, members and blocks.
- Single-statement `if`/`foreach` bodies are usually written without braces on the next line:
  ```csharp
  if (pluginTypes != null)
      return pluginTypes;
  ```
- `using` directives at the top, outside the namespace, `System.*` first and then alphabetical. Remove unused usings in files you touch.
- One public type per file, file name = type name, folder = namespace (`FreePIE.Core.ScriptEngine.Python.Ast` lives in `FreePIE.Core/ScriptEngine/Python/Ast/`).

### Naming
- Types, methods, properties, events, public constants: `PascalCase`. Interfaces prefixed with `I`.
- Private fields: `camelCase` **without** underscore prefix; assign in constructors with `this.field = field;`.
- Private constants: `PascalCase` in new code (older files have `camelCase` consts, leave them).
- Locals and parameters: `camelCase`. Use `var` when the type is obvious.
- Events published on the event aggregator: `XxxEvent` classes in an `Events` folder.
- Script-facing global members follow the scripting API (often lowercase, e.g. `x`, `setPressed`), not C# conventions. Don't rename them.

### Language usage
- Stay within C# 7.3 / .NET 4.8. No nullable reference types, records, `switch` expressions, file-scoped namespaces, etc.
- Properties are mostly written as `get { return x; }`; expression-bodied members are rare. Follow the file you are in.
- LINQ and method-group style (`.Select(Assembly.LoadFile)`, `.ForEach(SetPluginProperties)`) is common and preferred over manual loops when it reads well.
- Constructor injection via Ninject; use `Func<T>` factories for transient instances (see `MainMenuViewModel`).
- Fields that never change after construction are `readonly`.
- Communicate between components through `IEventAggregator` / `IHandle<T>` rather than direct references.
- GUI: View/ViewModel pairs by Caliburn naming convention (`FooView.xaml` + `FooViewModel.cs`), ViewModels derive from `PropertyChangedBase`/`Screen` and use `NotifyOfPropertyChange(() => Prop)`.
- No XML doc comments (`///`); the codebase doesn't use them.

### Tests
- MSTest (`[TestClass]`, `[TestMethod]`, `[TestInitialize]`), Rhino Mocks (`MockRepository.GenerateStub<T>()`, `.Stub(...).Return(...)`).
- Derive from `TestBase` when you need the Ninject kernel helpers (`Get<T>`, `Stub<T>`, `WhenCalling<T>`).
- Test method names are sentences in snake case describing behavior: `Names_are_filtered_by_what_has_been_written`. BDD-style classes (`When_listing_all_core_plugin_types` with a `Context()` initializer) also exist; match the file you add to.
- Add or update tests for changes in `FreePIE.Core` logic (script engine, code completion, AST, filters).

## Comments

Comments explain **why**, the code explains **how**.

- Write a comment only when the reason behind the code isn't obvious: threading constraints, IronPython quirks, workarounds for device/SDK bugs, non-obvious performance trade-offs, why something must be called in a particular order.
- Don't write comments that restate what the code does, narrate a change ("added X", "fixed Y", "new method"), or label obvious sections.
- Good (from `PythonScriptDebugger`):
  ```csharp
  // Must be called by the script thread before it ends, tracing that is left on slows down all scripts
  ```
- Bad:
  ```csharp
  // Loop through all plugins and set properties
  plugins.ForEach(SetPluginProperties);
  ```
- Style: `//` line comments, sentence case, short. No commented-out code.

## Git and commits

- **Always ask before committing.** Never commit, amend, push, or create branches/PRs unless the user has explicitly said yes for that specific change.
- **Before each commit, review the diff and remove unnecessary comments** you added: anything that describes *what/how* instead of *why*, change-narration, leftover debug notes, and commented-out code. Keep only comments that explain non-obvious reasons.
- Also check the diff for stray debug output, unused usings, and accidental formatting churn in untouched lines.
- Make sure the solution builds and the tests pass (apart from the known failures above) before proposing a commit.
- Commit messages: short imperative English summary, as in the existing history (e.g. `Analyze the script in the background during code completion`). Reference an issue as `#123 ...` when there is one.
- Work goes on `feature/<name>` branches and is merged to `master` via pull request.
- Never commit `.vs/`, `bin/`, `obj/`, `TestResults/`, `Output*/`, `packages/` or `*.user` files.
